# WebGPU kernels Hugging Face : package npm, 207 kernels versionnés et suite Fleet

## Points clés
- Hugging Face publie @huggingface/kernels (package npm) et une collection initiale de 207 kernels WebGPU hébergés sur le Hub, chaque kernel étant un paquet versionné contenant manifeste, shaders, cas de correction et cas de benchmark.
- Fleet : une application web (exécutable dans le navigateur) pour lancer des tests de correction et des benchmarks sur le GPU local ; avec consentement, chaque exécution contribue des données privées pour analyser fiabilité et performances par appareil.
- Interface d’utilisation : getKernel(repoID, contractVersion) retourne une fonction invoquable avec des entrées typées et formes de tenseurs ; l’exécution nécessite un navigateur/OS/GPU/driver offrant WebGPU (vérifiable par "gpu" in navigator).
- Résultats comparatifs (Apple M4, tests sur 809 cas compatibles) : gains mesurés vs ONNX Runtime Web (ORT WebGPU) — 2,57x plus rapide (moyenne géométrique), 1,90x au médian ; 629 victoires / 176 défaites / 4 égalités. Les timings excluent les frais de préparation (chargement, compilation, upload/download).
- Les kernels incluent plusieurs variantes par opération (p. ex. Add a des variantes pour formes égales, broadcast vectorisé, scalaire, etc.) ; la sélection de variante dépend de forme, device et contrat, sans changer l’API applicative.

## Points clés
- Deux nouveaux jeux de test ajoutés au Open ASR Leaderboard : Monsoon en-IN (Indian English) et Monsoon hi-IN (Hindi). Chaque jeu existe en split public (auto-évaluation possible) et split privé (évaluations centralisées par Hugging Face).
- Conception centrée sur la variance, pas le volume : 4 888 locuteurs, splits speaker-disjoints, plus de la moitié des locuteurs n’apparaissent qu’une seule fois ; 12 attributs par segment (ex. région, âge, genre, appareil, occupation, éducation, revenu, ville).
- Collecte : conversations spontanées dual‑canal, segmentées en un locuteur par clip ; large couverture géographique (EN: 428 districts / 30 états, HI: 202–295 districts) et diversité d’appareils (315–582 modèles, aucun >2.1%).
- Qualité & annotation : pipeline de QC automatisé (identification de langue, détection de playback, SNR, DNSMOS P.808), transcription humaine multi‑tours avec séparation stricte des rôles ; pour le hindi, chaque span est accompagné d’une lattice d’orthographes acceptées.
- Scoring spécifique pour le hindi : usage de l’OIWER (Orthographically‑Informed WER) et outil open‑source voi‑oiwer (disponible sur PyPI) pour éviter que l’orthographe annotateur‑dépendante fausse les WERs.
- Illustration empirique : deux systèmes proches en WER global peuvent diverger fortement selon la zone géographique (écarts types jusqu’à ~1.68 points selon zone), montrant que le WER agrégé masque des disparités régionales et socio‑techniques.

## Points clés
- Finetuning multi‑vector (ColBERT/LateOn) sur domaine médical (mLateOn‑medical) : 1M paires, 14,5 h sur une RTX 3090 (pic 17,5 GB VRAM) ; gain de +0,062 NDCG@10 vs meilleurs zero‑shot, rank‑1 passé de 75,8% → 84,9%.
- Point de départ recommandé : checkpoints pré‑supervisés (unsupervised / pre‑supervised) s’adaptent mieux au domaine que checkpoints « finis » ; une projection fraîche sur un backbone fort peut aussi suffire (25k paires proches des checkpoints existants).
- Perte recommandée pour paires question‑passage : MultiVectorMultipleNegativesRankingLoss ; version Cached/GradCache pour découpler taille effective de batch de la mémoire GPU (utile pour petits GPU).
- Troncature des documents = problème majeur sur textes longs (ex. moyenne 941 tokens) : lever le cap de longueur améliore NDCG jusqu’à 0,24. Configurer model_max_length et caps du checkpoint.
- Index : stockage token‑par‑token peut être volumineux (ex. 200k passages ≈ 45 GB fp16) ; combiner token pooling (HierarchicalTokenPooling), quantization (fast‑plaid 1‑bit residuals) et pruning ramène l’index à tailles deployables (ex. ~1,45 GB dans l’expérimentation) avec perte de qualité minime.
- Optimisations pratiques mesurées : punctuation skiplist réduit l’index ~9.6% et améliore légèrement la qualité ; scale de la softmax doit rester proche de 1.0 (ne pas réutiliser scale=20 des dense).
