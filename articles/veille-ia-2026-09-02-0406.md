# BenchMIRT — dissocier sécurité et raisonnement dans les benchmarks LLM

## Points clés
- BenchMIRT applique une approche d’Item Response Theory multidimensionnelle (MIRT) au niveau des questions (prompts) pour estimer quelles capacités sous-jacentes expliquent la performance sur chaque item.
- Modèle entraîné sur les résultats de 100 LLMs, 16 benchmarks et >34 000 questions ; il a retrouvé indépendamment deux dimensions dominantes : sécurité et raisonnement général.
- BenchMIRT identifie la difficulté et la « discrimination » de chaque question ; conserver 10 % des questions triées a généralement suffi à préserver le classement des capacités, 50 % reproduit encore mieux le bilan complet.
- Capacité de prédiction : BenchMIRT prédit correctement si un modèle répondra correctement à une question tenue hors échantillon dans 79 % des cas vs 70 % pour une stratégie naïve basée sur le score moyen.
- Limitations publiques notées : entraînement sur modèles publiés jusqu’à mars 2025 (généralisation aux générations plus récentes non démontrée) ; dimensions découvertes dépendent du jeu de benchmarks fourni ; risque d’usage malveillant (on peut supprimer questions informatives de sécurité).
- Compromis méthodologique : score moyen du benchmark est légèrement meilleur pour classer la performance sur items aléatoires ; BenchMIRT apporte en revanche une granularité question‑par‑question.

## Points clés
- Hugging Face publie aujourd’hui @huggingface/kernels (npm) et une collection initiale de 207 kernels WebGPU sur le Hub ; chaque kernel est un package versionné contenant interface, templates WGSL, cas de correction, cas de benchmark et instructions. (Disponible maintenant)
- Fleet (webgpu-kernels-fleet.hf.space) est une suite de tests/benchmarks exécutée dans le navigateur ; avec le consentement de l’utilisateur, chaque run peut envoyer des preuves privées pour aider à déceler régressions et optimiser les variantes. (Disponible maintenant)
- Les kernels exposent des variantes par forme/données/devices ; les contrats de kernel ont des versions séparées des opsets ONNX, permettant stabilité API côté JS tout en faisant évoluer les implémentations. (Disponible maintenant)

- Exécution dépend de WebGPU dans le navigateur (vérifiable par "gpu" in navigator) ; disponibilité et performances varient fortement selon navigateur, OS, GPU et driver. (À surveiller)

# Monsoon (Voice Arena) : nouveaux jeux de test ASR pour l’Inde (en‑IN, hi‑IN) sur l’Open ASR Leaderboard

## Points clés
- Hugging Face ajoute quatre splits Monsoon (public + privé pour en‑IN et hi‑IN) au Open ASR Leaderboard ; les splits publics sont téléchargeables pour auto‑évaluation, les privés sont réservés aux évaluations contrôlées par Hugging Face.
- Jeu de données orienté variance plutôt que volume : 4 888 locuteurs, plus de la moitié des locuteurs n’apparaissent qu’une seule fois ; top‑10 contributeurs = 2,8–6,8 % de la durée.
- Métadonnées étendues : 18 colonnes par segment (12 métadonnées incluant district, état, handset model, âge, genre, éducation, occupation, revenu, années dans le district, etc.), permettant désagrégation par population.
- Données enregistrées en conversations non scriptées, dual‑channel puis segmentées en segments mono‑locuteur (VAD : split à 2 s de silence / soft cap 15 s) ; pipeline : screening linguistique, contrôles automatisés (LID, détection playback, SNR, DNSMOS P.808), transcription humaine en 5 niveaux avec séparation des tâches.
- Hindi : références orthographiques multi‑variantes fournies sous forme de lattices ; score rapporté = OIWER (Orthographically‑Informed WER) ; outil open‑source voi‑oiwer (PyPI) publié pour reproduire le calcul.
- Exemple d’usage : deux systèmes proches en WER global peuvent diverger fortement par zone géographique (variations par zone mesurées jusqu’à ~1,7 points WER), montrant que l’agrégat masque des disparités.

# Modernisation guidée par l’IA : enseignements actionnables tirés du cas Bupa
