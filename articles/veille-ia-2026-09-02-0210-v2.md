# BenchMIRT : décomposer les scores de benchmarks LLM au niveau des prompts

## Points clés
- BenchMIRT applique la théorie des réponses aux items (MIRT) à l’échelle des questions de benchmarks LLM : entraîné sur 100 modèles open-weight, 16 benchmarks et >34 000 questions.  
- L’analyse a retrouvé de manière stable deux dimensions dominantes sur cet ensemble : sécurité et raisonnement général ; certaines évaluations se recouvrent ou s’alignent différemment que prévu (ex. BBQ s’aligne davantage avec le raisonnement).  
- BenchMIRT estime, par question, la difficulté et la discrimination sur chaque dimension et permet de classer les questions les plus informatives.  
- Réduction possible : conserver 10 % des questions peut globalement préserver l’image des capacités ; 50 % correspond souvent très bien au benchmark complet.  
- Prédiction : BenchMIRT prédit correctement la réponse tenue hors observation 79 % du temps (vs 70 % pour une stratégie naïve).  
- Limitations signalées : entraînement sur modèles distribués jusqu’en mars 2025 (pas de garanties sur générations ultérieures) ; dimensions dépendantes du jeu de benchmarks choisi ; risque que la transparence et la sélection de questions permette d’affaiblir les évaluations de sécurité.

- Article d’analyse pratique (El Camino Digital) : « Quand un score unique trompe — démonstration pas à pas avec benchmarks mixtes ». (à publier avec une infographie explicative).

# WebGPU kernels Hugging Face : collection versionnée, npm @huggingface/kernels et Fleet

## Points clés
- Hugging Face publie sur le Hub une collection initiale de 207 kernels WebGPU, chacun versionné et accompagné d’un "kernel card" (contrat, cas de correction, benchmarks, instructions).
- Package npm disponible : @huggingface/kernels sert de loader entre un repo de kernel sur le Hub et une application Web (appel via getKernel avec ID de repo et version de contrat).
- Fleet (web) permet d’exécuter en navigateur des tests de correction et de performance et, avec consentement utilisateur, d’envoyer des résultats privés pour améliorer la sélection de variantes.
- Résultats comparatifs donnés : sur Apple M4, sur 809 cas comparables, les kernels HF ont été 2.57x plus rapides (geometric mean), 1.90x au médian (629 victoires, 176 défaites, 4 égalités) — mesures limitées au temps GPU effectif (sans setup/compilation/transfert).
- WebGPU et les performances varient selon navigateur, OS, GPU et driver ; disponibilité à vérifier en JS par la présence de "gpu" dans navigator.

# Monsoon (Voice Arena) — jeux de test en‑IN / hi‑IN sur l’Open ASR Leaderboard

## Points clés
- Monsoon ajoute deux jeux (public+privé) pour l’anglais indien (en‑IN) et le hindi (hi‑IN) au Open ASR Leaderboard ; ensembles publics accessibles pour auto‑évaluation.
- 4 888 locuteurs, 4 splits indépendants et 12 champs démographiques par segment (ex. district, âge, genre, appareil) ; plus de la moitié des locuteurs n’apparaissent qu’une fois.
- Conception centrée sur variance plutôt que durée : neuf axes d’analyse contrôlés (géographie, âge, genre, vocabulaire, appareils, environnement acoustique, type/rythme de parole, multi‑références).
- Le hindi est évalué via une grille d’orthographes acceptées (lattice) et l’OIWER (Orthographically‑Informed WER) ; outil voi‑oiwer publié sur PyPI pour reproduire ce calcul.

### Solo-entrepreneurs sans budget, temps ni compétences numériques
- Intégrer dans tes workflows GitHub Actions existants la combinaison setup-python with allow-prereleases: true et check-latest: true — à tester. C'est une modification minimale qui permet d'exposer automatiquement ton code aux RC sans attendre des images officielles.
- Pour tout script ou utilitaire Python que tu distribues (ex. scripts de publication, extraction de données du blog) : ajouter une étape "installer et exécuter les tests" dans CI contre la pré-release via les flags ci‑dessus — à tester.
- Surveiller actions/python-versions pour l'arrivée d'images 3.15 RC/stable et planifier une mise à jour simple du workflow une fois disponible — à surveiller.
